<section id="snapshot">

## 30 秒摘要

MerchantOps Copilot 是一个面向中小电商经营运营负责人的本地 Alpha。它把只读经营数据查询和企业知识检索放进同一分析流程，展示 SQL、指标口径、日期范围、文档引用和风险。当前具备三个固定演示场景与安全边界，但开放问题、真实模型、部署和用户价值尚未验证。

</section>

<section id="context">

## 背景与目标

经营分析往往需要同时查询订单、商品和流量数据，以及活动规则、指标定义和复盘资料。只做 Text-to-SQL 会遗漏业务口径，只做知识检索又无法回答数据变化。

项目围绕制度查询、经营分析和联合归因三个假设场景验证“数据 + 知识 + 可核验证据”的工作流。目标用户假设尚未经过真实访谈。

### 我的职责

- 负责产品定义、场景研究和证据型经营分析流程设计
- 负责 SQL 安全、角色隔离、缓存限流和故障降级等架构决策
- 完成核心代码实现，或将需求拆解为 AI 可执行任务并审查交付
- 设计并执行固定评测、危险 SQL、性能检查和 Bad Case 验收

</section>

<section id="research">

## 关键洞察与问题重定义

同一句运营问题可能同时需要数据变化和业务规则。更重要的是，SQL 可执行不等于业务口径正确：语法错误会失败，口径错误却会产生看似合理的结论。

因此问题从“电商问数机器人”重定义为“如何在受限数据权限下输出可以由运营人员复核的经营判断”。

</section>

<section id="solution">

## 方案与关键决策

- 问题先区分知识、数据、混合和不支持路径。
- SQL 使用 SQLGlot、表字段白名单、强制行限制和只读账户设计约束；账户权限本次未复测。
- 回答展示 SQL、指标口径、日期范围、知识引用和风险。
- Redis 提供缓存和限流代码；关键服务不可用时返回明确失败或降级结果。

当前知识检索是关键词排序，不是语义 RAG。数据问答主要覆盖固定模板，混合分析串行调用两个工具，三个核心场景的结论主要使用手写组合逻辑。

</section>

<section id="architecture">

## 系统架构与当前能力

```text
Streamlit
    ↓
FastAPI（固定三角色）
    ↓
规则与固定场景编排
  ↙             ↘
MySQL         本地知识文件
  ↘             ↙
可核验证据回答
    ↓
Redis 缓存与限流
```

已实现三角色登录、固定模拟数据驾驶舱、Markdown/TXT/PDF 知识导入、关键词检索、SQL 安全、执行 Trace、Redis 缓存限流代码和固定评测工件。

自然语言数据查询、混合分析、统一证据展示和 Dify 工作流为部分实现。Docker/Caddy 只有配置；LangGraph、语义 RAG、统一结果 Contract 和公开 HTTPS 仅在规划中。

</section>

<section id="bad-cases">

## Bad Case

- 开放式数据问题可能超出固定 SQL 模板。
- 复杂同义表达可能被关键词检索漏召回，扫描 PDF 无 OCR。
- 混合流程串行执行，缺少通用证据守卫。
- 文档冲突或过期时缺少人工确认流程。
- MySQL/Redis 离线时无法完成完整查询。
- 大量能力仍处于未提交工作区，缺少稳定版本锚点。

</section>

<section id="reflection">

## 复盘与下一步

当前最小目标不是增加 LangGraph 或更多工具，而是恢复隔离环境并重新运行现有测试、危险 SQL 和固定评测，使当前能力可以复现。真实模型、Dify、部署和用户价值继续保持尚未验证。

</section>
