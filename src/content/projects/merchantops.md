<section id="snapshot">

## 30 秒摘要

MerchantOps Copilot 试图解决的不是「让 AI 回答电商问题」，而是让运营人员知道答案来自经营数据、业务知识，还是两者共同构成的证据。项目当前处于开发中，已完成产品边界和工作流设计，尚未公开效果指标。

</section>

<section id="context">

## 背景与目标

真实运营判断经常需要同时查询订单、商品、流量等结构化数据，以及活动规则、指标定义和复盘记录等非结构化知识。手工切换工具效率低，而通用模型容易忽略企业自己的指标口径。

目标是用统一入口接收自然语言问题，在明确安全边界后调用合适工具，并让每个结论都能回到证据。

### 我的职责

- 从直播电商运营经历提取典型问题和决策场景。
- 拆分知识类、数据类和混合类问题。
- 定义 Agent 路由、只读 SQL、安全校验、证据合并和拒答。
- 规划评测指标与 Bad Case 记录方式。

</section>

<section id="research">

## 调研与关键洞察

同一句运营问题可能包含不同任务。例如「为什么本周转化下降」既需要查询数据变化，也需要结合活动、库存或内容策略解释。单一 RAG 或单一 Text-to-SQL 都无法覆盖完整链路。

第二个洞察是：SQL 可执行不等于答案正确。指标口径、时间范围和业务过滤条件错误，往往比语法错误更危险。

</section>

<section id="reframe">

## 重新定义问题

原问题：如何做一个电商问数机器人？

重新定义后：如何把运营问题路由到正确证据源，在不越过数据安全和指标口径边界的前提下，输出可追溯的判断？

</section>

<section id="solution">

## 方案与关键决策

### 决策一：先路由，后生成

Agent 先判断问题属于知识、数据还是混合类型，再调用对应工具，减少所有问题都进入同一条链路造成的噪声。

### 决策二：查询层只读

生成 SQL 只能访问允许的表和字段，并拒绝写入、删除和结构修改操作。

### 决策三：证据不足时拒答

当数据缺失、口径不明确或知识库无覆盖时，系统返回需要补充的信息，不把常识推测写成企业经营结论。

### 被放弃的方向

没有直接做一个连接全库的自由问答 Agent。它能更快产出演示，但无法说明指标口径、安全边界和错误责任。

</section>

<section id="architecture">

## 系统工作流

```text
自然语言问题
      ↓
问题分类与约束识别
  ↙       ↓       ↘
知识检索  只读 SQL  混合任务
  ↘       ↓       ↙
证据合并与冲突检查
      ↓
结论 + 引用 + 建议 + 风险
```

计划中的最小技术栈为 Python、FastAPI、SQL 与本地知识库。第一版不引入复杂多 Agent 协作，单路由器加明确工具边界足以验证核心假设。

</section>

<section id="validation">

## 验证方法与当前结果

评测将拆成五类：问题路由准确性、SQL 可执行率、指标口径正确性、引用完整性、证据不足时的拒答正确性。

当前已完成问题分类、核心链路和安全边界定义；可运行 Demo 与测试集仍在建设，因此没有公开准确率或效率提升数字。

</section>

<section id="bad-cases">

## Bad Case

- 用户使用模糊的「销量」概念，但数据库同时存在付款、发货和签收口径。
- SQL 语法正确，却遗漏退款或测试订单过滤条件。
- 知识库没有覆盖特定平台规则，模型仍尝试给出确定建议。
- 混合问题只执行了数据查询，没有检索导致变化的活动背景。

</section>

<section id="reflection">

## 复盘与下一步

项目当前最重要的不是增加更多工具，而是用真实问题测试路由、口径和拒答。只有这些边界稳定后，才值得扩展更复杂的 Agent 协作。

下一步完成最小 Demo，并为每个失败案例记录问题类型、错误环节、修复策略和回归结果。

</section>
